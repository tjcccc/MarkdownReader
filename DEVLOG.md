# DEVLOG

## 2026-08-05

- Release: cut `0.4.0` — minor bump over 0.3.0 for the whole-document WebKit renderer, GitHub-inspired presentation, persistent display controls, and offline syntax highlighting.
- Replaced the custom TextKit renderer with one whole-document `WKWebView`. This removes the split responsibilities that made table selection, code-block selection, padding, rounded backgrounds, and blockquote layout depend on `NSLayoutManager` drawing geometry. The SwiftUI document window, native TOC sidebar, toolbar, file flow, pasteboard integration, external-link handling, and image lightbox remain native.
- `MarkdownHTMLRenderer` now uses `cmark-gfm` directly with the table, task-list, strikethrough, autolink, and tag-filter extensions. It returns safe HTML plus heading titles/levels/anchors for the sidebar. Raw Markdown HTML remains disabled.
- Added a GitHub-inspired local page in `MarkdownHTMLDocument`: controlled light/dark CSS tokens, a 900px reading column, GitHub-like headings/tables/blockquotes/code, continuous browser selection, fenced-code language labels, and per-block copy controls.
- Added offline syntax highlighting with the common-language Highlight.js 11.11.1 browser build. Fenced language tags are honored, untagged blocks use automatic detection, unsupported language tags stay readable as plain code, and highlighting can be disabled without reloading the document.
- Added a native display popover backed by `AppStorage`: font size (13–26pt), line spacing (1.2–2.0×), System/Light/Dark theme, syntax-highlighting toggle, and reset. Updates are sent to the existing page rather than recreating the web view.
- Relative document images are served through `markdown-reader-resource://document/`. The resolver canonicalizes paths, resolves symlinks, and rejects parent traversal; the scheme exposes only validated document files and the exact bundled highlighter resource. The page also has a restrictive CSP, blocks network content, and opens external links outside the web view.
- Removed the unused `swift-markdown-ui` and NetworkImage dependency chain; the project now pins only `swift-cmark` 0.5.0. Deleted the 706-line attributed renderer, 478-line custom text view, and their TextKit-specific tests.
- Verification: compiler-warning-free macOS arm64 build exits 0; focused unit suite passes 15/15, covering GFM HTML, safe raw-HTML handling, headings/anchors, initial page options/CSP, preference bounds, local-resource traversal rejection, real custom-scheme highlighter and local-image loads, and in-place setting updates. WebKit snapshots were inspected in light/plain-code and dark/highlighted states; table padding, blockquote inset, continuous code surfaces, and Swift/Python syntax colors render cleanly. The documented Release command exits 0 and the built app contains the offline `highlight.min.js` resource.
- Full test action: `MarkdownReaderUITests.testExample` and `testLaunchPerformance` passed, confirming repeated app launches. The template `MarkdownReaderUITestsLaunchTests.testLaunch` then hit its known 120-second environmental runner timeout; this run repeatedly logged `DebuggerVersionStore: no debugger version`, and Xcode was interrupted after it stalled while finalizing the already-failed test. No product crash or assertion was reported.

## 2026-07-26

- Release: cut `0.3.0` — minor bump over 0.2.1. New user-visible capability (per-block language tag and copy button on fenced code), rounded code styling at both scales, inline-code padding, and three rendering fixes. One known issue ships with it, recorded below and in the README: the thin white seam across code blocks is still unresolved.
- Fixed: an inline-code span that wraps inside an indented list item painted a stray highlighted strip across the leading indent of the continuation line. Cause is AppKit drawing, not our attributes — `NSLayoutManager` builds each fill rect from the *line fragment* rect (left edge = container edge) rather than the *used* rect (left edge respects `headIndent`), so the indent got filled.
- Fix in `SelectableMarkdownView.swift` only: new `IndentAwareBackgroundLayoutManager` overrides `fillBackgroundRectArray(_:count:forCharacterRange:color:)` and clamps each rect's left edge to the enclosing line's used rect. `drawBackground(forGlyphRange:at:)` is overridden solely to capture the draw origin, since fill rects arrive origin-offset while used rects are in container coordinates. Rects with no matching line pass through unclamped rather than being dropped.
- Inline code now gets 2pt of horizontal padding on each side. Attributed strings have no padding attribute, so the same override inflates the fill rect; runs are tagged with a custom `.inlineCodeSpan` key in the renderer so block-level fills (quotes, fenced code) are excluded. Padding is applied *after* the indent clamp, so a wrapped span keeps the same inset on its continuation lines. Vertical padding was left alone — the fill already spans the line height, and inflating it would collide with neighbouring lines.
- Selection safety: NSTextView routes selection highlighting through the same primitive, and a selection band *should* cover the indent. The override therefore applies the **left** clamp and the inline-code treatment only when the fill color matches the `.backgroundColor` attribute at the range start. (Superseded in part later the same day: the **height** clamp below deliberately does apply to selection fills too, so selection no longer takes an entirely unmodified `super` path.)
- The view now builds an explicit TextKit 1 stack (`NSTextStorage` → custom layout manager → `NSTextContainer` → `ReadingTextView(frame:textContainer:)`). Previously the stack was implicit and only fell back to TextKit 1 lazily, when `layoutManager` was first touched during image hit-testing.
- Rounded corners, both scales: inline code chips are now drawn by the override as rounded rects (radius 4) instead of by `super`'s square fill; fenced code blocks use a new `RoundedTextTableBlock` (an `NSTextTableBlock` subclass overriding `drawBackground(withFrame:in:characterRange:layoutManager:)`, radius 8), since `NSTextBlock`'s own background drawing is always square. Block quotes were left square — not part of the request.
- Fenced code blocks gained a language tag and a copy button, sitting in a reserved strip at the top of the box (`CodeBlockMetrics.headerHeight`, added as extra `.minY` padding on the cell so the controls can never overlap a long code line). They're `CodeBlockHeaderView` overlays on the text view, not text, so they stay out of document selection and copied text. The tag is omitted when the fence carries no language hint; the button copies that block's source and flips to "Copied" for 1.5s.
- Renderer now tags each code block's characters with `.codeBlockInfo` (language + source); the view enumerates that attribute, and repositions the overlays from layout geometry in `layout()`.
- Thin white seam reported across a code block, just under the language tag. Diagnosis by elimination: rendering the same document offscreen (real renderer, same block drawing) produced one continuous 72pt box band with no seam, so the box fill isn't at fault — the only thing present in the app but not offscreen is the header overlay. The strip it occupies is the block's **top padding, which contains no glyphs**; the box background is drawn per glyph range, so any partial repaint of that strip (scrolling exposes exactly it) repaints the text view's white background and nothing else. Fix: the header now paints that strip itself — `textBackgroundColor` then `CodeBlockMetrics.background`, reproducing the box's composite — and spans the full box width (controls inset by `padding`) so no edge is left uncovered. Verified pixel-wise: every column through the box reads a uniform 240, i.e. the self-painted strip is indistinguishable from the box fill and does not darken it.
- **Still open — the seam is NOT fixed.** The user still sees it after the change above, and it was never reproduced locally (fresh windows, icon clicks, and symbol swaps all stayed clean; scrolling couldn't be driven, as that needs assistive access this environment lacks). So the glyph-less-strip diagnosis is at best incomplete: the header now paints its own strip opaquely and a seam still appears, which points elsewhere — candidates worth checking next are the boundary between the block's drawn frame and the first line fragment (a sub-pixel gap at fractional Retina geometry), and whether `NSTextBlock.drawBackground` is invoked more than once per box with adjacent frames. Deferred by the user to a later polishing pass; the self-painted strip was kept because it is correct in its own right and pixel-verified not to darken the box.
- Colour de-duplicated: `CodeBlockMetrics.background` is now the single source, with the renderer's `Style.codeBackground` pointing at it, so the box, inline chips, and the header's repaint can't drift apart.
- Selection painted the gap between paragraphs — most visibly as a tall band above a code block when selecting into it. Measured offscreen rather than guessed (scratch program over the real renderer, dumping line-fragment vs used rects): a paragraph's **last** line fragment is 36pt tall against a 24pt used rect, the 12pt excess being `paragraphSpacing`; mid-paragraph lines have **zero** excess, because line spacing sits inside the used rect. So fill rects are now clamped to the used rect's bottom — this one applies to selection fills as well as backgrounds, and the measurements say it cannot introduce gaps between selected lines within a paragraph.
- Copy control is now an icon (SF Symbol `doc.on.doc`, swapping to `checkmark` for 1.5s) rather than a text pill — no title width to reserve, so the truncation machinery is gone. The header row is centred in the box's reserved top strip instead of hugging the code line, which read as lopsided.
- Pointing-hand cursor bug found and fixed: `copyButtonFrame` converted `button.bounds` (origin 0,0) from the *header's* coordinate space, so the hit rect landed at the header's corner and the test never matched — the I-beam always won. Now converts `button.frame`. Added a `PointingHandButton` subclass (cursor rect + `cursorUpdate` + a `.cursorUpdate`/`.mouseEnteredAndExited` tracking area) so the cursor is claimed whether the event routes to the button or to the text view underneath.
- Header refinements after first look: the language tag moved to the **leading** edge (header now spans the box width — tag left, button right, via plain constraints rather than a stack, so an untagged fence still keeps its button at the right). The copy button's width is pinned to the widest of "Copy"/"Copied", measured once on a throwaway button, so the label can't truncate to "Co…" mid-flash and the live button is never briefly titled "Copied" before first display. Hovering the button shows a pointing hand, via two complementary paths — the text view's `mouseMoved`/`cursorUpdate` interception (the existing image-cursor pattern, needed because NSTextView keeps restoring the I-beam) and `resetCursorRects` on the header itself.
- Verified: build exits 0; unit suite 14/14 (three consecutive full runs of `-only-testing:MarkdownReaderTests`). Note: the very first run after adding the tests reported `tagsInlineCodeSpans` failing, then passed in isolation and in every subsequent full run — consistent with that invocation's test bundle linking a pre-change app binary, not a product defect. Copy buttons verified live: clicking each block's button put exactly that block's source on the pasteboard, "Copied" renders in full, and a pasteboard sentinel survives a fresh launch (nothing fires the action spuriously). The pointing-hand cursor is **not** visually verified — automating a hover needs assistive access, which `osascript` doesn't have here. Visually confirmed against a repro doc — wrapped inline code in both bulleted and numbered items now starts flush with its glyphs (plus its padding), and block-quote / fenced-code fills are unchanged (uniform, not ragged-left, no added padding). Test split: the drawing itself isn't unit-testable, but the renderer contracts the view depends on now are — `MarkdownAttributedRendererTests` asserts inline code carries `.inlineCodeSpan` and that a fence carries `.codeBlockInfo` with the right language and source (and no language when the fence is untagged), so deleting a marker can't silently drop the styling with a green build. ⌘A selection was not visually re-checked (a system permission dialog held keyboard focus during the run); selection is unaffected by construction via the color guard above.

## 2026-07-25

- Release: cut `0.2.1` — patch bump over 0.2.0. Icon artwork only; no behavior, API, or feature-surface change.
- App icon replaced: swapped the emoji-style spiral notebook for a new open-book render (yellow/white pages on a blue cover), supplied by the user as a 2048×2048 transparent PNG.
- Re-composited rather than plain-resized. The source art nearly filled its canvas (alpha bbox 1892×1614 of 2048, ~39pt margins at 1024-equivalent) — far tighter than any macOS icon. Cropped to the alpha bbox, scaled to an 880pt-wide footprint, and centered at y≈490 on a fresh 1024 canvas (optical center sits slightly high, leaving bottom room as the previous icon did). All 7 slot sizes are resampled from a 2048 master, not chained down, and tagged sRGB (the source was untagged).
- `Contents.json` unchanged — same 7 filenames and the same reuse pattern across 1x/2x slots.
- macOS 26 (Tahoe) icon behavior, verified empirically on 26.5.2 via `NSWorkspace.icon(forFile:)` against the actual built app:
  - Tahoe auto-adapts legacy free-form icons by compositing them onto a system-drawn light-gray squircle plate and shrinking the art to fit. Our icon renders this way; the book reads well within the plate at the chosen 880pt footprint.
  - Probes confirmed this is inherent to the appiconset format, not a defect here: full-bleed opaque art gets cleanly masked to the squircle by Tahoe, but would render as a hard square on the macOS 15.1 deployment target. Art with transparent margins (needed for 15.1) always gets plated on Tahoe — see Ghostty for the same double-rounded artifact.
  - A Tahoe-native squircle would require either an Icon Composer `.icon` file or compositing the book onto an opaque background — both are design changes to the supplied artwork, deferred pending a decision.
- Verified: `xcodebuild -scheme MarkdownReader -project MarkdownReader.xcodeproj -destination 'platform=macOS,arch=arm64' -quiet clean build` exits 0 (exit code captured directly, not through a pipe; the only `error:` string in the log is simulator noise inside a method name — `sharedServiceContextForDeveloperDir:error:` — from the unrelated out-of-date CoreSimulator warning).
- Small-size legibility, checked by upscaling the actual renders rather than eyeballing at native size:
  - 32pt and up: reads clearly as an open book — yellow left page, white right page, blue cover and curled corner all survive.
  - 16pt on a plain light background (i.e. free-form, as macOS 15.1 would draw it): weak. The white right-hand page washes out against white and the blue page-curl breaks up into stray pixels, leaving mostly a yellow block. This is a mild regression from the previous icon, whose solid yellow notebook held its silhouette at 16pt.
  - 16pt as macOS 26 actually composites it: acceptable. The system's gray plate backs the art and restores contrast on the white page, so the open-book shape still reads. Since the plate is what this machine renders, the 16pt weakness is largely theoretical today.
